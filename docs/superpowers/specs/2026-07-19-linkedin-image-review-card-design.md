# LinkedIn Image Drafting and Human-Only Publishing Design

**Date:** 2026-07-19

**Status:** Approved design; implementation not started

**Repository:** `Pratikn07/pmm-career-mcp`

**Deployment branch:** `codex/supabase-migration`

## Context

PMM Career MCP currently supports private, versioned LinkedIn text drafts and a guarded text-publishing workflow. The user's intended operating model is broader:

- A scheduled ChatGPT task runs each morning, researches a topic, and saves a private LinkedIn draft.
- A draft may contain one image or an ordered gallery of up to four images.
- Images may be generated by ChatGPT or uploaded by the user.
- The scheduled task must never create a publishable preview, upload media to LinkedIn, or publish.
- The user later opens the conversation, reviews and revises the draft with ChatGPT, and explicitly decides whether to publish.
- The exact text, visibility, image order, alt text, and checksums presented for approval must be the exact version sent to LinkedIn.

The existing LinkedIn connection is valid and includes `w_member_social`. Publishing remains disabled in production while this feature is built and verified.

## Goals

1. Support private LinkedIn drafts with one to four JPG, PNG, or GIF images.
2. Accept both ChatGPT-generated images and user-uploaded images through ChatGPT file parameters.
3. Keep scheduled tasks technically unable to preview or publish.
4. Put exact preview creation and publishing behind a human-operated ChatGPT Apps SDK review card.
5. Preserve immutable versioning, checksums, short-lived approval, one-use consumption, concurrency protection, and no automatic publish retry.
6. Store draft images privately in Supabase Storage with per-user authorization.
7. Keep all production writes limited to the single configured Supabase user and the connected LinkedIn member.
8. Retain independent master switches for LinkedIn publishing and image publishing, both off by default.

## Non-goals

- Editing LinkedIn profile fields such as headline, About, career history, skills, or recommendations. LinkedIn's approved APIs do not provide general member-profile editing for this app.
- Automated or unattended LinkedIn publishing.
- Letting a scheduled task create a preview token or approval secret.
- Adding an OpenAI API key or another billable image-generation service without separate user approval.
- Supporting video, documents, link cards, polls, or more than four images in this version.
- Making stored media public or returning permanent public URLs.
- Retrying an ambiguous LinkedIn media upload or post creation automatically.

## Decision

Use one MCP connection with two sharply separated action categories:

1. **Model-visible draft actions** perform research, create and revise text, attach validated images, set order and alt text, save immutable versions, and notify the user. They cannot create preview approval or publish.
2. **App-only review actions** create the exact preview and publish the approved version. They are available only to the review-card UI and hidden from the model with Apps SDK tool visibility metadata.

This design uses the ChatGPT Apps SDK review card because the safety boundary must be enforced by tool availability and server checks, not only by prompt wording. The scheduled task and the conversational model may prepare content, but neither receives the actions or secret needed to publish.

## Alternatives considered

### Two MCP connections

One draft-only MCP could be assigned to scheduled tasks and a separate publisher MCP used interactively. This creates a strong boundary but duplicates connection setup, OAuth, discovery, operations, and user-facing configuration. It is not selected for the first version.

### One MCP with ChatGPT “Always ask” permissions

This is a useful additional UI safeguard but is not a sufficient server-side boundary. A model-visible preview or publish action would still be callable by a scheduled run. It is not selected as the primary control.

## Superseded behavior

This specification supersedes the following assumptions in the original text-only design:

- `preview_post` is no longer model-visible and is not read-only. Creating a preview persists a one-use approval capability, so it is an app-only private write.
- `publish_linkedin_post` is no longer model-visible. The replacement app-only publish action is invoked only from the review card after an explicit human click and confirmation.
- Publishing is no longer text-only; it may include one to four immutable image references.
- A natural-language instruction such as “do not publish” remains useful, but is not the enforcement mechanism.

The original text checksum and one-use preview concepts remain, extended to cover ordered media and alt text.

## Architecture and trust boundaries

### Model-visible layer

The model may use tools to:

- research approved public YC sources;
- draft or revise post text;
- accept one to four ChatGPT-generated or user-uploaded image files;
- attach, replace, remove, and reorder draft media;
- write concise alt text;
- save a new immutable draft version;
- read private draft history and launch the review card;
- notify the user that a draft is ready.

The model-visible review-card launcher may select a draft and render its current data. It must not create a preview record, issue an approval secret, upload anything to LinkedIn, or invoke publishing.

### App-only layer

The review card may invoke two app-only tools:

- `create_exact_linkedin_preview`
- `publish_exact_linkedin_post`

Both descriptors use `_meta.ui.visibility: ["app"]`. They are omitted from the model's tool namespace. The publish action also requires a fresh approval capability returned only in widget-private response metadata.

### Server layer

The server remains the authority for ownership, version status, checksums, token expiry, token consumption, configuration switches, LinkedIn connection ownership, and state transitions. It never trusts a checksum, media list, object path, visibility, or post text supplied by the browser without reloading the immutable version from Postgres.

## Workflow

### Scheduled morning flow

```text
scheduled ChatGPT task
  -> research approved YC/public sources
  -> draft post text
  -> generate or accept up to four images when supported
  -> validate and save private media
  -> save immutable draft version
  -> notify the user
  -> stop
```

The schedule must not call a preview action, upload to LinkedIn, or publish. Because those actions are app-only, this is enforced independently of the scheduled prompt.

The recommended schedule instruction is:

> Research today's approved topic and save a private LinkedIn draft in PMM Career MCP. You may prepare up to four draft images with alt text. Do not create an exact preview, do not upload anything to LinkedIn, and do not publish. Notify me when the private draft is ready, then stop.

### Interactive review flow

```text
user opens the conversation
  -> user and ChatGPT brainstorm/revise
  -> every revision creates a new immutable version
  -> ChatGPT opens the review card for the selected version
  -> user clicks “Create exact preview”
  -> card displays the locked text, visibility, image order, alt text, checksum, and expiry
  -> user clicks “Publish this exact version to LinkedIn”
  -> explicit confirmation dialog
  -> server revalidates and performs one publish attempt
```

Opening or rendering the card is not approval. “Create exact preview” is also not publishing. Only the final confirmed app-only publish action can make a LinkedIn write.

## ChatGPT Apps SDK integration

### File inputs

The draft-media tool exposes top-level file fields using `_meta["openai/fileParams"]`. ChatGPT supplies file objects containing a short-lived `download_url`, `file_id`, and optional MIME type and file name. The server fetches and validates the bytes immediately; it does not persist the ChatGPT download URL.

The Apps SDK documents file parameters and widget-only tool visibility at [Tool descriptor metadata](https://developers.openai.com/apps-sdk/reference#_meta-fields-on-tool-descriptor). Widget APIs for file selection, upload, download URLs, and widget-invoked tools are described under [Capabilities](https://developers.openai.com/apps-sdk/reference#capabilities).

### Proposed tools

Model-visible tools:

- `draft_linkedin_post` — create the initial private text draft.
- `revise_linkedin_post` — create a new private immutable text version.
- `attach_linkedin_post_images` — validate and attach one to four file parameters, ordered with alt text; creates a new version.
- `revise_linkedin_post_images` — replace, remove, reorder, or change alt text; creates a new version.
- `get_linkedin_post_draft` — return a selected private draft version.
- `open_linkedin_review_card` — render the review component for a selected version without creating preview state.

App-only tools:

- `create_exact_linkedin_preview` — reload the selected immutable version, validate it, persist a short-lived one-use preview, and return display data plus a widget-only approval capability.
- `publish_exact_linkedin_post` — consume the capability, upload the locked media, create the exact LinkedIn post once, and record the result.

The names may be aligned with existing code during implementation, but their visibility and responsibilities must not change. Existing `preview_post` and `publish_linkedin_post` must not remain callable by the model under old names.

### Widget-private approval material

`create_exact_linkedin_preview` returns safe display fields in `structuredContent`. The one-use approval capability is returned only in the tool result `_meta`, which the Apps SDK exposes to the widget as `window.openai.toolResponseMetadata` and does not expose to the model. The widget passes it to `publish_exact_linkedin_post` through `window.openai.callTool`.

The approval capability is:

- cryptographically random;
- stored only as a hash at rest;
- bound to owner subject, draft ID, version, whole-post checksum, and expiry;
- valid for at most 15 minutes;
- one-use and atomically consumed;
- never logged, included in model-visible content, or returned after consumption.

## Review card

The review card displays:

- full, exact post text without truncation;
- visibility (`CONNECTIONS` or the supported LinkedIn equivalent);
- all images in exact publish order;
- alt text next to each image;
- draft ID and immutable version;
- abbreviated whole-post checksum with an option to inspect the full value;
- preview expiration time;
- validation status and any blocking errors.

The card provides:

1. **Create exact preview** — an app-only private write.
2. **Publish this exact version to LinkedIn** — disabled until the preview succeeds.
3. A confirmation dialog that names the version, number of images, and visibility.

Changing any draft field requires returning to the conversation, saving a new version, and creating a new exact preview. The card cannot edit the locked preview in place.

## Image ingestion and validation

The server accepts one to four images per version. Each file must pass all checks before the version can become ready for review.

### Allowed content

- JPEG (`image/jpeg`)
- PNG (`image/png`)
- GIF (`image/gif`)
- no more than 20 MiB per file as a conservative application policy, independent of LinkedIn's documented pixel limit;
- fewer than 36,152,320 decoded pixels;
- no more than 250 GIF frames;
- non-zero width and height;
- alt text required and limited by the application to 120 Unicode characters.

LinkedIn supports JPG, PNG, and GIF, documents a 36,152,320-pixel limit and a 250-frame GIF limit, and recommends alt text under 120 characters even though the API field permits more. See the official [Images API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api?view=li-lms-2026-05).

### Validation controls

- Stream the download with a finite connection/read timeout and a hard byte cap.
- Require HTTPS and follow only a small, bounded number of redirects.
- Reject loopback, link-local, private, reserved, and metadata-service destinations after every DNS resolution and redirect to prevent SSRF.
- Verify magic bytes and decoded structure rather than trusting the declared MIME type or extension.
- Reject malformed, truncated, decompression-bomb, excessive-dimension, and excessive-frame files.
- Compute SHA-256 over the exact original bytes that will later be uploaded.
- Dedupe identical bytes for the same owner without allowing cross-owner object access.
- Strip no metadata and perform no lossy transformation in the first version. Preview and LinkedIn upload use the exact stored bytes.

If ChatGPT's file URL expires before ingestion completes, the tool fails safely and asks the user or scheduled run to attach/regenerate the image again.

## Supabase Storage and request authorization

### Private bucket

Create a private bucket such as `linkedin-draft-media` through the Supabase dashboard or Storage API. Do not insert into or mutate the `storage` schema directly; Supabase documents the Storage schema as read-only metadata. See [Storage schema design](https://supabase.com/docs/guides/storage/schema/design).

Configure bucket-level MIME and file-size restrictions as defense in depth. Private-bucket downloads require either an authenticated request subject to RLS or a short-lived signed URL, as documented in [Storage bucket fundamentals](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [Private downloads](https://supabase.com/docs/guides/storage/serving/downloads).

Object paths are namespaced by the authenticated Supabase subject, for example:

```text
<owner_subject>/<sha256-prefix>/<media-id>/<sanitized-filename>
```

RLS policies on `storage.objects` allow `SELECT`, `INSERT`, and required cleanup operations only when the first path component equals `auth.jwt()->>'sub'` and the bucket ID is exact. Cross-subject access is denied. Policies follow Supabase's [Storage access-control guidance](https://supabase.com/docs/guides/storage/security/access-control).

### Request-scoped user token

The HTTP auth layer currently validates a bearer token and discards its request context. Implementation must propagate the validated request-scoped bearer token and subject into the per-request MCP server dependencies without persisting, logging, or returning the token. A Supabase Storage client uses the publishable key plus that user JWT so RLS remains the authorization boundary.

The existing Supabase access-token hook sets the token audience to this MCP resource. Live verification must prove that Supabase Storage accepts that custom-audience user token. If it does not, implementation stops for a security/design decision. It must not silently add a service-role or secret key, weaken RLS, or expose the service-role key. Supabase notes that secret/service-role keys bypass RLS and must be limited to trusted backend components in [Database security](https://supabase.com/docs/guides/database/secure-data).

### Preview delivery

The review card receives only short-lived authenticated or signed image URLs, with a maximum lifetime matching the 15-minute preview. Permanent public URLs are prohibited. The object path and any storage credential remain absent from model-visible output where they are not needed.

## Postgres data model

The implementation plan may refine names, but the normalized model is:

### `career_mcp.post_media`

- `id uuid primary key`
- `owner_subject uuid not null`
- `object_path text not null`
- `sha256 text not null`
- `mime_type text not null`
- `byte_size bigint not null`
- `width integer not null`
- `height integer not null`
- `frame_count integer not null default 1`
- `original_filename text null`
- `created_at timestamptz not null`

Constraints include positive size/dimensions/frame count, allowed MIME values, lowercase 64-character SHA-256, uniqueness of `(owner_subject, sha256)`, and uniqueness of `object_path`.

### `career_mcp.post_draft_media`

- `post_draft_id uuid not null`
- `post_version integer not null`
- `position smallint not null check (position between 0 and 3)`
- `media_id uuid not null`
- `alt_text text not null check (char_length(alt_text) between 1 and 120)`
- composite foreign key to the immutable post version
- foreign key to `post_media`
- primary key `(post_draft_id, post_version, position)`
- uniqueness of `(post_draft_id, post_version, media_id)`

Database triggers or a transactionally enforced service invariant ensure no version has more than four media rows and that every referenced media owner matches the draft owner. Media references cannot be changed after an immutable version is committed; modifications create a new version.

### Preview/publish records

Existing preview and publish-attempt records gain:

- the whole-post checksum;
- media count;
- capability hash and expiry;
- atomic consumed timestamp;
- attempt phase (`preflight`, `uploading_media`, `creating_post`);
- per-image upload registration/asset URN state;
- final post URN or explicit ambiguous result.

No raw approval capability or LinkedIn access token is stored in these audit rows.

## Canonical checksum contract

The whole-post checksum is SHA-256 over a versioned, length-delimited canonical byte sequence. It includes:

1. checksum format identifier;
2. draft UUID;
3. immutable version number;
4. exact normalized text bytes;
5. exact visibility value;
6. media count;
7. for each media item in ascending position:
   - position;
   - media SHA-256;
   - MIME type;
   - exact alt-text UTF-8 bytes;
8. the byte length before every variable-length field.

Text normalization is limited to the already-defined storage normalization performed before saving a version; publishing never re-normalizes or reformats the saved value. Length prefixes prevent concatenation ambiguity. A format identifier permits future schema evolution without accepting old checksums under new rules.

Any text, visibility, media bytes, media order, MIME type, or alt-text change produces a new immutable version and checksum and invalidates all prior unconsumed previews.

## LinkedIn publishing protocol

### Preflight

Inside a transaction or equivalent atomic lock, the server:

1. authenticates the allowed Supabase subject;
2. verifies `LINKEDIN_PUBLISH_ENABLED=true`;
3. verifies `LINKEDIN_IMAGE_PUBLISH_ENABLED=true` when media exist;
4. verifies the connected LinkedIn member and required scope;
5. reloads the immutable version and ordered media;
6. recomputes the whole-post checksum;
7. verifies capability hash, owner, version, checksum, expiry, and unused status;
8. atomically consumes the capability and acquires the publish-attempt lock;
9. revalidates stored object hashes before any LinkedIn request.

### Media upload

For each image in locked order, the server calls LinkedIn's image initialization endpoint, uploads the exact stored bytes to the returned upload URL, and records the returned `urn:li:image` asset. LinkedIn's official sequence is documented in the [Images API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api?view=li-lms-2026-05).

The connected app has the write-only `w_member_social` scope. LinkedIn documents that this is sufficient to initialize and upload member-owned images but not to GET them through the versioned Images API. Therefore, a definite successful upload response is the boundary for continuing; the MCP does not request an additional restricted read scope or claim that it independently polled the asset state.

A one-image post uses a standard post media object. A two-to-four-image post uses LinkedIn's organic multi-image post format, documented in the [MultiImage Post API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/multiimage-post-api?view=li-lms-2026-02). Although LinkedIn permits more items, this application caps the gallery at four.

### Final post creation

After every image upload is definitely successful, the server makes exactly one final post-creation request using the locked text, visibility, ordered asset URNs, and alt text. The general post contract is documented in LinkedIn's [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-04).

There is no automatic retry of the final create-post request after dispatch. Token refresh may occur only before post creation when the server can prove no post request was sent.

## State and failure handling

The minimal state model is:

- `draft` — privately editable by creating new versions;
- `ready_for_review` — selected immutable version passes validation;
- `previewed` — a live exact preview exists;
- `uploading_media` — approval consumed and image operations started;
- `publishing` — all image uploads definitely succeeded and the one final post request is in flight;
- `published` — definite success with LinkedIn post URN;
- `media_upload_failed` — definite pre-post failure; no LinkedIn post was created;
- `media_upload_unknown` — upload outcome ambiguous; stop and do not create the post automatically;
- `publish_failed` — final post request definitely failed;
- `publish_unknown` — final request may have succeeded; user must inspect LinkedIn before any new attempt.

Rules:

- Validation or storage failure leaves the immutable version unpublished and produces no preview.
- If any image initialization or byte upload fails definitely, remaining uploads stop and no post is created.
- If an image upload outcome is ambiguous, the state becomes `media_upload_unknown`; no post is created and no automatic retry occurs.
- Uploaded but unused LinkedIn assets may be orphaned. Their URNs are audited for later manual cleanup if LinkedIn supports it; cleanup is not allowed to trigger a post.
- If final post creation is ambiguous, state becomes `publish_unknown`; the server never retries and instructs the user to check LinkedIn manually.
- Concurrent publish calls for the same preview produce at most one network attempt.
- A consumed or expired capability can never be reused, even after definite failure. A new exact preview is required for another user-authorized attempt.

## Configuration switches

- `LINKEDIN_PUBLISH_ENABLED` — existing master publishing switch; default `false`.
- `LINKEDIN_IMAGE_PUBLISH_ENABLED` — new image-upload/publish switch; default `false`.

Both stay false during development, migration, deployment, and non-publish testing. After the full rollout checklist passes, the user may authorize enabling both in Railway. Enabling the switches makes the app-only flow operational; it does not make publishing automatic or expose publish actions to the model.

Text-only publishing continues to require the app-only exact-preview flow. An image post additionally requires the image switch.

## Security requirements

- Permit exactly the configured `ALLOWED_SUBJECT` at the MCP resource layer.
- Enforce ownership again in SQL queries and Supabase Storage RLS.
- Keep Supabase, LinkedIn, and approval secrets server-side; never render or log them.
- Use a request-scoped Supabase user token and discard it after the request.
- Use private storage only and short-lived preview URLs.
- Pin the review component's Apps SDK CSP to the minimum Railway/MCP and Supabase Storage origins required; do not grant unrestricted network access.
- Sanitize file names for display and object paths; never use them for filesystem paths.
- Protect file fetching against SSRF, oversized responses, redirect abuse, MIME spoofing, malformed images, decompression bombs, and parser hangs.
- Recompute stored-byte SHA-256 immediately before LinkedIn upload.
- Require explicit final confirmation in the widget even if ChatGPT app permissions are configured to “Always allow” low-risk actions.
- Mark external-write tool annotations accurately. Preview creation is not read-only; final publishing has `readOnlyHint: false` and `openWorldHint: true`.
- Preserve structured audit records without recording post text unnecessarily in operational logs.

## Testing strategy

### Unit tests

- Accept valid generated/uploaded JPG, PNG, and GIF files.
- Reject incorrect magic bytes, MIME mismatch, oversized bytes, excessive pixels, excessive GIF frames, zero dimensions, malformed/truncated files, decompression bombs, and unsafe URLs.
- Accept one through four ordered images; reject zero for attach operations and reject five or more.
- Enforce alt text length and Unicode behavior.
- Verify per-image SHA-256 dedupe is owner-scoped.
- Verify canonical whole-post checksums change for text, visibility, order, bytes, MIME type, and alt-text changes.
- Verify file download URLs and bearer tokens are never stored or logged.

### Database and Storage tests

- Apply reversible PostgreSQL migrations and validate all constraints and foreign keys.
- Prove draft-version immutability and maximum four media rows.
- Prove owner mismatch and cross-subject reads/writes fail.
- Prove private objects have no public URL and signed URLs expire.
- Prove Storage operations use the Storage API and RLS, not direct `storage` schema writes.
- Perform a live gate test that the custom-audience Supabase user JWT works with Storage. Stop if it fails.

### Tool-boundary tests

- Verify draft and launcher tools are model-visible.
- Verify `create_exact_linkedin_preview` and `publish_exact_linkedin_post` use `_meta.ui.visibility: ["app"]` and are absent from the model namespace.
- Verify the launcher cannot create preview state.
- Verify approval material exists only in widget-private `_meta`, not `structuredContent`, content text, or logs.
- Verify scheduled-task prompts can create a draft but cannot discover or call preview/publish tools.

### Publishing tests

- Test text-only, single-image, and two-to-four-image payload construction against mocked LinkedIn endpoints.
- Verify exact image order, exact bytes, alt text, visibility, and text.
- Verify expired, replayed, stale, wrong-owner, wrong-version, wrong-checksum, and malformed capabilities fail before a LinkedIn call.
- Verify concurrent calls produce one publish attempt.
- Verify partial upload failure, ambiguous upload, final definite failure, and final ambiguous result enter the correct terminal state.
- Assert no retry after image ambiguity or final post dispatch.
- Assert an actual LinkedIn post is never made in automated tests.

### End-to-end verification

- Run the full test suite, typecheck, build, production dependency audit, migrations, and Docker build/smoke tests.
- Deploy only `codex/supabase-migration` to the existing Railway project.
- Refresh the ChatGPT developer-mode app so updated tools and component metadata are discovered.
- Run a scheduled-flow smoke test that creates only a private draft.
- Run an interactive review-card test through exact preview with publishing switches still off.
- Confirm a disabled-switch publish attempt fails before LinkedIn.

## Scheduled image-generation capability gate

OpenAI documents that ChatGPT tasks can use apps and that Apps SDK tools can accept files. The documentation does not guarantee that every scheduled-task environment can generate an image and pass it directly as an MCP file parameter. See [Tasks in ChatGPT](https://help.openai.com/en/articles/10291617-tasks-in-chatgpt) and [Apps in ChatGPT](https://help.openai.com/en/articles/11487775-connectors-in).

Before relying on scheduled images, perform a non-publishing capability test. If the scheduled environment cannot hand an image file to the MCP, the schedule saves the text draft plus a detailed image brief or prompt. The user can then generate or upload the image in the interactive conversation. The implementation must not add an OpenAI API key, create a new paid service, or incur a billable upgrade without asking the user first.

## Acceptance criteria

- The MCP stores private drafts with zero to four images and publishes only versions with zero to four fully validated images.
- Both generated and user-uploaded images are accepted through ChatGPT when file parameters are available.
- The scheduled task can research and save drafts but cannot create an exact preview or publish.
- The model cannot call either app-only action.
- The user sees and confirms the exact immutable version through the review card.
- Any content or media change invalidates prior preview approval.
- Image bytes remain private and are protected by owner-scoped authorization.
- Single- and multi-image LinkedIn payloads are correct and deterministic.
- Ambiguous external outcomes never trigger automatic retries.
- Both publishing switches default to false and are enabled only after explicit user approval and successful verification.
- No secrets are exposed, and no live post is made during implementation or verification without a separate, explicit instruction.
